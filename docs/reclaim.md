# RentBack wallet and reclaim implementation

Wallet connection uses `@solana/kit` 8.2.0, `@solana/kit-plugin-wallet` 0.19.0 and Wallet Standard discovery. Wallet app selection is explicit. Auto-connect and wallet selection storage remain disabled. Wallet Standard account events are handled by the plugin; RentBack subscribes through its React hooks and shows an account selector only when the app exposes multiple authorized mainnet accounts.

`@solana-mobile/wallet-standard-mobile` 0.6.0 is dynamically registered after mount on secure Android pages. The SDK handles environment compatibility. The identity is RentBack, the canonical production URL from `src/lib/site.ts`, and its absolute `/rentback-icon.svg` URL. Authorization is not restored across reloads. The local adapter is labeled "Use installed wallet". Android Chrome/Seeker requires a physical-device test; a narrow desktop viewport is not an MWA test.

## Reclaim boundary

- Scanner projections are unchanged. Reclaim has its own domain and decimal-string API DTOs.
- `/api/reclaim` verifies the full mainnet genesis hash, reads both token programs using base64 account data, checks the owning program and decoded token owner, excludes native/uninitialized accounts, and fetches uncached rent for every actual data size.
- The instruction allowlist is exactly one `SetComputeUnitLimit`, one `SetComputeUnitPrice`, then discriminator `38` (`WithdrawExcessLamports`) generated by the installed official SPL Token or Token-2022 client. There are no transfer, tip, close, burn, approval, swap or authority-change instructions in generated reclaim plans.
- Source is the eligible token account. Destination, fee payer and signing authority are always the connected/scanned owner. No destination is accepted from the UI.
- Version-0 transactions use no address lookup tables. Batches are packed greedily by actual complete serialized wire length, including the signature, under the 1,232-byte limit.
- All batches are packed with both fixed-width Compute Budget instructions before size measurement. A 200,000-CU probe simulation measures consumption; the final limit is the ceiling of measured consumption plus 10%, with a 10,000-CU floor and a 200,000-CU ceiling. Missing usage or exceeding the ceiling fails closed. The final transaction is simulated again and its exact message is used for RPC fee estimation before review. Review expires after 30 seconds. Each transaction requires a fresh explicit click. After confirmation, remaining candidates are re-fetched and re-simulated before another signature can be requested.
- For signing wallets, RentBack compares returned message bytes against the reviewed message, revalidates accounts/rent at submission, simulates the signed transaction, and sends with preflight enabled. Changed balances, rent, ownership, program or account size stop submission.
- Sending-only Wallet Standard/MWA wallets sign and broadcast themselves. RentBack passes the same allowlisted simulated message and verifies the confirmed message before crediting reclaimed SOL. Such wallets do not expose signed bytes for inspection before their own broadcast; this transport necessarily relies on the selected wallet honoring the submitted message.
- There is no server keypair and no sign-message/sign-in path.

## Completion and recovery

An intent is saved in session storage before the wallet request. Known signatures are saved before RentBack submits, so an HTTP response loss does not discard them. Signing-only rejection is a failure with no server submission. Ambiguous broadcasts remain pending and block another reclaim for that wallet. Users can check status; expiry requires finalized block height beyond the last valid height plus a safety margin. No automatic resend is performed.

Successful receipts remain visible across retries and reloads in the same browser tab. Remaining candidates are freshly computed and successful sources excluded when advancing the current plan. Reclaimed SOL is derived from confirmed source-account balance changes and reconciled against the destination balance plus network fee. Scan estimates are never reported as actual reclaimed amounts. The UI reports gross reclaimed SOL and distinguishes network fees.

## Complete-message / Phantom priority-fee correction

The old builder supplied no Compute Budget instructions. Phantom documents adding priority fees during signing when the transaction is unsigned, has no budget configuration and remains under 1,232 bytes after enhancement. The screenshots show the app estimating 5,000 lamports while Phantom displayed 80,000 lamports. This supports the hypothesis but does NOT prove that the rejected real message changed only Compute Budget instructions: that message was not captured and cannot be recovered from the screenshots or existing console logs. No further signature was requested to obtain it.

The deterministic regression models that documented mutation: a six-account message becomes eight instructions, with unchanged fee payer, blockhash and withdrawal metas/data and two Compute Budget instructions inserted first. Strict byte equality rejects it. This is a fixture, not a captured Phantom message.

New transactions use `@solana-program/compute-budget` 0.18.1 official instruction builders. Price is fixed at 1,000 micro-lamports per CU, with no automatic escalation: `ceil(units * 1000 / 1000000)` lamports, at most 200 lamports. This deliberately low fee may need an explicit policy review under congestion. All monetary arithmetic remains bigint and API monetary values remain decimal strings. Only bounded non-monetary CU counts use the official numeric u32 API.

Both client and server retain exact signed-message equality. Wallet-added budget changes are NOT whitelisted. Development builds alone emit sanitized decoded message comparisons on rejection; all production builds disable that logging: instruction order/count, program IDs, public account metas, fee payer, blockhash and decoded budget values. No signatures, wallet objects or raw arbitrary instruction payloads are logged. The error shown to users identifies which message fields changed. Normal signed transactions add signatures only and compare equal.

Existing `rentback:reclaim-receipts:v1` history is not cleared or migrated. Historical budget-less receipts have a dedicated reconstruction path for confirmation/accounting ONLY. New reviews and submissions without an explicit budget fail closed.

Validation includes the exact 58 -> 52 confirmed -> 6 remaining recovery fixture, all requested message tampering cases, size-aware repacking, fee estimation for the final simulated message, and UI fee display. `reclaim-mainnet-readonly.test.ts` is an opt-in, wallet-free integration test that only fetches and simulates; it writes public message fields and results to `docs/reclaim-readonly-result.json`. The 58-account sizing report uses actual source addresses/programs with synthetic positive excess solely to measure historical batch sizes, not as a reclaim review.
